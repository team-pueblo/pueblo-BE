# Issue-first workflow

## 작업 순서와 권한

사용자가 이 워크플로로 개발 작업을 요청하면 다음 순서를 따른다.

1. 저장소와 템플릿 확인
2. 목적 및 TODO를 작성하여 GitHub 이슈 생성
3. 실제 발급된 이슈 번호로 `feat/#<번호>` 브랜치 생성
4. 구현 및 검증
5. `[feat] #<번호> - <커밋메시지>`로 커밋 후 해당 브랜치 푸시
6. 저장소 PR 템플릿에 맞춰 PR 생성
7. 이슈·PR 링크와 검증 결과를 보고하고 사용자 머지를 기다림

이 스킬로 이슈부터 PR까지 진행하라는 요청은 그 범위의 이슈 생성·수정, 작업 브랜치 생성, 커밋, 푸시, PR 작성 권한을 포함한다. 이미 허용된 단계마다 재확인을 반복하지 않는다. 사용자가 계획만 요청하거나 푸시·PR 생성을 제외했다면 그 제한을 따른다. 도구 및 환경의 승인 요구는 그대로 지킨다.

**머지는 항상 사용자가 한다.** PR merge, auto-merge, merge queue 등록, 기본 브랜치 직접 푸시를 실행하지 않는다. 이슈를 수동으로 완료 처리하지 않고 PR의 연결 문구를 통해 사용자 머지 후 닫히게 한다.

## 1. 저장소와 템플릿 확인

- 작업 경로, Git 상태, 원격 저장소, 현재 브랜치, 기본/대상 브랜치와 적용되는 `AGENTS.md`·기여 규칙을 확인한다. 저장소명이나 기본 브랜치를 고정하지 않는다.
- `.github/ISSUE_TEMPLATE/`의 실제 Markdown/YAML 템플릿을 읽고 작업에 맞는 것을 선택한다. `.github/pull_request_template.md`, 대문자 변형 또는 `.github/PULL_REQUEST_TEMPLATE/`도 확인한다.
- 템플릿의 제목, 순서, 필수 필드와 체크리스트를 보존한다. 안내 주석은 실제 내용으로 채우고 Markdown 이슈 템플릿의 YAML 메타데이터는 본문에서 제외한다. 이슈 폼은 입력 항목을 빠짐없이 본문으로 옮긴다.
- 템플릿이 없으면 임의 양식으로 게시하지 말고, 위치나 대체 양식을 확인한다. 로컬 조사와 본문 초안 작성은 계속할 수 있다.
- 기존 변경사항은 삭제·초기화·무조건 stash하지 않는다. 현재 작업에 속하는 변경과 다른 작업을 구분하고, 불명확한 변경을 임의로 커밋하지 않는다. 필요하면 깨끗한 별도 worktree에서 진행한다.
- 사용자에게 받은 기존 이슈가 있으면 그 이슈를 확인해 재사용한다. 같은 작업의 기존 이슈·PR·브랜치가 있는지 확인해 중복 생성하지 않는다.

## 2. 이슈 먼저 작성

- 코드 구현 전에 목적, 변경 범위, 완료 조건과 실행 가능한 TODO를 이슈 템플릿에 맞춰 작성한다. TODO에는 구현과 필요한 검증을 포함하고 처음에는 `- [ ]`로 둔다.
- 이슈를 생성한 뒤 응답에서 실제 번호와 URL을 확인한다. 번호를 예상하거나 템플릿 파일 번호를 사용하지 않는다.
- `team-pueblo/pueblo-FE`의 현재 템플릿은 `.github/ISSUE_TEMPLATE/custom.md`이며 `### 🔥PURPOSE`, `### 📒TODO`를 사용한다. 이는 참고값이며 실행할 때 저장소의 최신 파일을 다시 읽는다.
- 기존 이슈를 사용한다면 TODO가 작업 범위를 충분히 설명하는지 확인하고 보완한 뒤 구현한다.

## 3. 이슈 번호로 브랜치 생성

- 예: 이슈 `#12` → 브랜치 **`feat/#12`**. 사용자가 다른 이름을 명시하지 않는 한 `feature/12`, `feat/12` 등으로 바꾸지 않는다.
- 작업 대상 브랜치의 최신 상태를 기준으로 생성한다. 현재 다른 작업 브랜치를 무조건 기준으로 삼지 않는다.
- 쉘에서는 `git switch -c 'feat/#12' <확인한-기준-ref>`처럼 브랜치명을 따옴표로 감싼다.
- 같은 이름의 브랜치가 있으면 연결된 이슈와 변경사항을 확인해 재사용한다. 임의로 덮어쓰거나 삭제하지 않는다.
- 이미 구현된 작업을 정리해 달라는 경우에는 기존 변경을 보존하고 이슈 TODO에 완료된 항목을 사실대로 기록한다. 작업 순서를 지킨 것처럼 꾸미지 않는다.

## 4. 구현과 검증

- 이슈 TODO 범위에 맞게 작업하고 관련 없는 변경을 섞지 않는다.
- 프로젝트의 빌드·린트·테스트 중 변경에 필요한 검증을 수행한다. 시각 확인이 필요한 UI 작업은 가능하면 브라우저에서도 확인한다.
- 완료하고 확인한 TODO만 체크한다. 실행하지 못한 검사, 기존 실패와 새 실패를 구분한다.
- 원격 이슈 본문을 수정하기 전 최신 내용을 다시 읽고 다른 사람이 작성한 내용을 보존한다.

## 5. 커밋과 푸시

- 정확한 형식: **`[feat] #12 - 장바구니 주문 정보 레이아웃 적용`**.
- 번호는 이슈·브랜치와 일치해야 한다. 사용자가 별도 지시하지 않으면 커밋 유형은 `[feat]`, 메시지는 간결한 한국어로 작성한다.
- `git diff`와 staged diff를 확인하고 작업 관련 파일만 명시적으로 stage한다. 다른 작업이 있는 저장소에서 `git add .`를 사용하지 않는다.
- 실제 검사 결과를 확인한 후 커밋하고, 검증된 원격의 작업 브랜치에 일반 push한다. 강제 푸시나 커밋 이력 재작성은 별도 요청 없이 하지 않는다.
- 예: `git commit -m '[feat] #12 - 장바구니 주문 정보 레이아웃 적용'`, `git push -u origin 'feat/#12'`. `origin`은 사전 확인한 경우에만 사용한다.
- 새로 발생한 미해결 검사 실패가 있으면 준비 완료로 보고하지 않는다. 문제를 수정하거나, 사용자가 검토용 제출을 원할 때 실패를 명시한 draft PR로 처리한다.

## 6. PR 작성

- base는 확인한 대상 브랜치, head는 작업 브랜치로 명시한다. 같은 head/base의 열린 PR이 있으면 새로 만들지 않고 갱신한다.
- PR 제목은 별도 저장소 규칙이 없으면 `[feat] #12 - 작업 요약` 형식을 쓴다.
- PR 템플릿의 모든 섹션을 실제 변경에 맞춰 채운다. 문제와 변경 후 동작, 검토 포인트, 참고 자료, 실제 검증 결과를 작성한다. 해당 없는 항목은 `해당 없음`으로 표시하고 실행하지 않은 테스트를 통과했다고 쓰지 않는다.
- `team-pueblo/pueblo-FE`의 현재 섹션은 `Summary`, `Description`, `PR Point`, `Reference`, `Test`이다. `Description`의 `- close:` 자리는 **`- Closes #12`**로 완성하여 연결한다. 사용자 머지 전에는 이슈를 직접 닫지 않는다.
- PR 생성 후 URL, base/head, 이슈 연결, 최종 본문을 확인한다.

## 원격 작업의 실패·재시도

- GitHub CLI 또는 제공된 GitHub 도구를 사용한다. CLI의 여러 줄 이슈·PR 본문은 임시 UTF-8 파일로 작성해 `--body-file`로 전달한다.
- 인증·권한·네트워크 문제는 환경의 승인 절차를 따른다. 해결되지 않으면 본문과 로컬 작업을 보존하고 실패한 단계와 재개에 필요한 조건을 보고한다.
- 생성 요청이 timeout되어 성공 여부가 불명확하면 원격에서 같은 이슈·PR이 생성됐는지 확인한 뒤에만 재시도한다. 확인할 수 없으면 중복 생성하지 않는다.

## 최종 보고

이슈 링크, 브랜치명, 커밋, PR 링크, 검증 결과와 남은 제한을 간결하게 보고한다. **“머지는 직접 진행해 주세요.”**라고 명시하고 종료한다.
