# pueblo 백엔드 설계 협의 기록


[주문 결제 시도 접수](order-payment-preparation.md)는 구현된 내부 계약이다. 결제 시도 영속화·취소 경합·만료 처리를 포함하며 실제 PG 승인·결제 결과 처리는 후속 범위다.
- 버전: v0.2 — 인터뷰 결정 반영, 상세 구현 설계 초안
- 작성일: 2026-10-24
- 기준: 사용자 제공 요구사항 v0.1, 이번 대화의 인터뷰 답변, 토스 Learner’s High 서버 3기 세션 자료
- 목적: 구현 전 서비스 경계·데이터 소유권·상태 전이·이벤트·검증 범위를 공유한다.

이 문서는 구현 완료 보고서가 아니다. **확정**은 인터뷰에서 선택한 정책이고, **설계 제안**은 이를 구현하기 위한 초안이다. 제안된 API·이벤트명·테이블·상태명은 아직 구현 계약으로 확정되지 않았다. 이전 단일 Spring 애플리케이션 안은 MSA 결정으로 대체한다.

현재 구현은 4개 서비스 골격, Outbox 발행·소비 중복 방지 인프라, Istio STRICT mTLS 배포 기반과 [회원 인증 API](member-auth.md), [카탈로그 조회·데이터 가져오기](catalog.md), [재고 상태 전이·내부 명령](inventory.md)까지다. [견적·주문 접수·재고 예약 연동·미결제 취소](orders.md)도 구현했으며 기본 비활성이다. 재고 이벤트의 실제 계약은 inventory 문서, 주문 계약은 orders 문서를 따른다. 아래 주문·결제 흐름 전체의 구현·검수가 끝난 것은 아니다.

## 1. 목표와 범위 — 확정

기술 검증을 우선하고 이후 실제 판매로 확장한다. 빠른 완성을 지향하되 완료 날짜는 미정이다. 핵심 검증 순서는 **결제 정합성 → 재고 동시성 → 조회 성능**이다. 자료에 등장하는 기술을 모두 도입하는 대신 문제·측정·변경·결과를 기록한다.

| 항목 | 1차 결정 |
| --- | --- |
| 언어·프레임워크 | Java / Spring |
| 서비스 구성 | 회원, 상품·재고, 주문, 결제의 4개 독립 실행·배포 서비스 |
| 저장소 | 현재 저장소의 Gradle 멀티모듈, 공통 코드는 최소화 |
| 데이터베이스 | MySQL 인스턴스 하나, 서비스별 DB·계정 분리 |
| 서비스 간 데이터 접근 | API·이벤트 사용. 교차 DB 조회·조인·트랜잭션 금지 |
| 메시징 | Kafka 단일 브로커, Transactional Outbox, DB 폴링 발행 |
| 흐름 조율 | 주문 서비스가 재고·결제·취소 흐름을 조율 |
| 인프라 | 서버 2대에 Kubernetes·MySQL·서비스·Kafka 공동 운영, 단일 클러스터 + Istio mTLS |
| 서버 한 대 | 4 vCPU / 메모리 4GB / 디스크 40GB. 디스크 종류 미확인 |
| 관측 | 요청 ID 기반 로그·기본 메트릭·실험 결과 기록 |
| 결제 환경 | 토스페이먼츠 테스트 연동 + 장애 재현용 모의 결제 서버 |
| 판매 형태 | pueblo 단일 판매자·새상품, 회원 구매만 허용 |

단일 MySQL·Kafka는 단일 장애 지점이다. 현재 구성은 데이터베이스·브로커·Kubernetes 제어 영역의 고가용성을 약속하지 않는다. 서버별 control plane·워크로드·영속 볼륨 배치와 자원 예산은 추가 설계가 필요하다. 서버 재시작 복구 검증에는 DB·Kafka 데이터의 영속화가 선행되어야 한다.

## 2. 기능 정책 — 확정

### 2.1 회원과 인증

- JWT 서명은 환경변수 `JWT_TOKEN` 비밀키를 사용하는 HS256으로 확정했다. RSA 키 파일·공개 키 조회 API는 사용하지 않는다. Access/Refresh 만료·세션·교체 정책은 유지한다.

- 이메일·비밀번호·닉네임·필수 약관 동의로 가입한다. 닉네임은 중복을 허용한다.
- 이메일의 일회용 인증 링크를 사용하고, 인증 후 가입 완료·구매를 허용한다.
- 필수 약관은 코드·설정으로 버전 관리하고, 동의 종류·버전·시각을 DB에 저장한다.
- JWT 액세스·리프레시 토큰을 사용한다. 액세스는 브라우저 메모리, 리프레시는 HttpOnly·Secure 쿠키에 보관한다.
- 액세스 유효기간은 최신 보안 요구에 따라 5분, 리프레시 최대 기한은 최초 로그인부터 14일이다. 교체해도 최대 기한은 연장하지 않는다.
- 리프레시는 매번 교체하고 재사용을 감지하면 해당 로그인 세션을 폐기한다. 정상 동시 갱신 요청의 오탐도 처리한다.
- 여러 기기 로그인을 허용하며 로그인 세션별로 관리한다. 로그아웃은 해당 세션, 비밀번호 재설정은 모든 세션을 폐기한다.
- 일회용 이메일 링크를 통한 비밀번호 재설정을 포함한다. 실제 이메일 발송과 개발·자동 테스트용 모의 발송을 모두 지원한다.
- 운영자는 초기 설정 명령으로 생성한다. 공개 회원가입으로 운영자 권한을 부여하지 않는다.

회원 서비스는 요청마다 자체 DB 세션과 Redis 보안 키를 확인해 폐기된 액세스 JWT를 거부한다. 주문 서비스는 회원 본인 조회 API로 세션 확인을 연동했다. 결제 서비스는 후속 구현 대상이다. 서명·만료만 검사하면 폐기된 세션의 JWT가 최대 5분간 사용될 수 있으므로, 세션 상태 확인 등 별도 설계가 필요하다.

### 2.2 상품·검색·저장 기능

- 상품 목록·상세, 브랜드·카테고리 필터, 검색·정렬·페이지네이션을 포함한 기존 P0 탐색 기능을 구현한다.
- MySQL 검색부터 구현하고 실행 계획·응답시간을 측정한 뒤 개선한다. 합성 상품 10만 개로 조회 성능을 검증한다.
- 품절 상품도 목록·검색에 노출한다. 상세 조회·관심 등록은 허용하고 구매는 차단한다. 비공개·삭제 상품은 공개 API에서 제외한다.
- 옵션 조합별 SKU로 재고를 관리한다. 옵션이 없어도 기본 SKU를 부여한다.
- 상품 이미지는 준비된 URL을 등록한다. 업로드 기능은 보류한다.
- 장바구니·바로 구매 모두 지원하며 같은 견적·주문 API를 사용한다.
- 장바구니와 주문의 동일 SKU 상한은 9개다. 주문 본문에 같은 SKU를 나누어 보내도 합산 검증한다.
- 장바구니에 담을 때 재고를 예약하지 않는다.
- 로그인 시 안내 후 비회원 저장 항목을 자동 병합한다. 관심목록은 합집합, 장바구니는 동일 SKU 수량을 합산한다.
- 병합 재시도는 수량을 중복 증가시키지 않는다. 상한 초과·판매 중지 등 거부 항목은 사유를 반환하고 로컬에 보존한다. 서버 확정 전 로컬 데이터를 삭제하지 않는다.
- 결제 완료 후 주문 당시와 SKU·수량이 같은 장바구니 항목만 삭제한다. 결제 중 수량을 변경한 항목과 바로 구매 항목은 유지한다.

### 2.3 견적·주문·배송

- 쿠폰은 보류한다. 배송비·서비스 수수료는 0원이다. 결제금액은 서버 판매단가 × 수량의 합계다.
- 금액은 KRW 정수로 계산하고 클라이언트 금액을 승인 근거로 사용하지 않는다.
- 견적 유효기간은 5분이고 재고를 예약하지 않는다. 주문 생성 시 가격을 재검증하고, 달라지면 재견적과 사용자 확인을 요구한다.
- 확정된 주문 금액은 결제 대기 기간에 고정한다.
- 주문 요청에 `202 Accepted`와 주문 ID를 반환한다. 프론트는 상태 조회로 재고 확보를 확인한 뒤 결제창을 활성화한다.
- 모든 SKU를 확보해야 주문이 결제 대기로 진행한다. 하나라도 부족하면 전체를 거부한다.
- 재고 확보 성공 시점부터 15분간 예약한다. 주문 접수부터 재고 예약 결과를 30초 안에 받지 못하면 중단 절차를 시작한다.
- 중단 이후 도착한 예약 성공은 해제한다. 예약·해제 메시지 순서가 뒤바뀌는 경우도 처리한다.
- 배송지는 주문 시 입력하고 수령인·연락처·우편번호·주소를 주문 스냅샷으로 보존한다. 국내 주소를 허용하며 주소록은 보류한다.
- 운영자 API로 송장 등록·출고·배송 완료를 처리한다. 택배사 연동은 보류한다.
- 마이페이지를 복원하지 않고 헤더에서 독립 주문 목록·상세 화면으로 진입한다. 본인 주문만 조회한다.

### 2.4 결제·취소·복구

- 결제 인증 결과를 받은 결제 서비스가 결제사에 즉시 승인 요청한다. 확인한 결과를 응답하고 Kafka로 주문 서비스에 전달한다.
- 외부 호출 결과가 불명확하면 확인 중으로 응답하고 결제사 조회로 대사한다. 성공 URL 도착만으로 결제 완료 처리하지 않는다.
- 서버 재시작 후에도 DB 기록으로 미완료 승인·환불을 자동 복구한다.
- 승인과 출고 전 전액 취소·환불을 1차에 포함한다.
- 취소와 출고가 경합하면 DB에서 먼저 확정된 처리를 우선한다. 취소 접수가 먼저 확정되면 출고를 차단하고 환불한다.
- 환불 요청과 환불 성공은 구분한다. 출고 전 전액 환불 성공 후 해당 주문의 재고를 정확히 한 번 복원한다.
- 15분 이후에도 결제사 장애로 승인 여부를 알 수 없으면 재고를 즉시 해제하고 결제 조회를 계속한다.
- 늦게 승인이 확인되면 재고를 재확보해 주문을 유지한다. 재확보에 실패하면 자동 전액 환불한다.
- 자동 재조회가 정해진 횟수 실패하면 운영자 확인 대상으로 전환한다. 기록을 보존하고 운영자 API로 재조회·재처리한다. 외부 알림은 보류한다.
- 자동 처리 대상은 결제사 장애 해소 후 1분 이내 복구를 목표로 한다. 재시도 한도 초과로 운영자 확인 대상이 된 건은 별도 추적한다.

## 3. 서비스 경계와 데이터 소유권 — 설계 제안

| 서비스 / 모듈 후보 | 소유 데이터 | 책임과 공개 기능 |
| --- | --- | --- |
| 회원 / `member-service` | 회원, 이메일 인증, 가입 동의, 로그인 세션·토큰 교체 이력, 비밀번호 재설정 | 가입·메일·로그인·갱신·로그아웃·본인 정보·운영자 인증 |
| 상품·재고 / `catalog-service` | 브랜드, 카테고리, 상품, 이미지 URL, SKU, 재고, 예약·확정·해제 이력 | 공개 조회·검색, 재고 예약·재확보·확정·해제·복원, 운영 상품·재고 관리 |
| 주문 / `order-service` | 견적, 주문·항목·가격·주소·동의 스냅샷, 흐름 진행 기록, 배송, 관심목록, 장바구니·병합 이력 | 견적·주문 접수·상태 조회, 재고·결제 조율, 취소·출고 경합 제어, 저장 기능 |
| 결제 / `payment-service` | 결제 시도, 승인·환불 기록, 웹훅, 외부 호출·대사·운영자 재처리 이력 | 승인·결과 조회·취소·환불·웹훅 검증, 테스트·모의 결제사 어댑터 |

관심목록·장바구니의 주문 서비스 배치는 4개 서비스 안에서 시작하기 위한 제안이다. 각 서비스는 자체 Outbox·소비 중복 방지 기록·멱등 요청 기록을 소유한다. 공유 엔티티·다른 서비스 저장소 의존은 두지 않는다. 라이브러리 공유는 요청 추적·보안 등 필요한 범위로 제한한다.

회원 ID는 인증 주체에서 결정한다. 서비스 간 명령의 호출자와 이벤트 생산자를 인증하고, 브라우저가 내부 재고·환불 명령을 직접 실행할 수 없게 한다. 서비스별 DB 마이그레이션은 해당 서비스가 소유한다.

## 4. 상태 전이와 불변 조건 — 설계 제안

### 4.1 주문

```text
PREPARING → PENDING_PAYMENT → PAYMENT_CONFIRMING → PAID
PAID → FULFILLING → SHIPPED → COMPLETED
PREPARING → ABORTING → CANCELED / REJECTED
PENDING_PAYMENT → EXPIRING → EXPIRED
PAID → CANCEL_PENDING → REFUND_PENDING → CANCELED
늦은 승인 확인 → 재고 재확보 중 → PAID / REFUND_PENDING
```

`PAYMENT_CONFIRMING`은 UI·조율 상태이며 결제사 승인 여부의 원장은 결제 서비스에 있다. 결제 미확정·늦은 승인·환불 대기는 별도 진행 기록으로 추적해 단순 만료 상태로 덮지 않는다. 출고 허용은 결제 성공과 재고 확정을 모두 확인한 경우로 제한한다. 출고 전 취소 범위에는 `FULFILLING`을 포함한다.

취소·출고는 주문 서비스의 동일 원장에 조건부 상태 변경으로 직렬화한다. 취소 접수 이후에는 환불 장애가 나더라도 출고가 가능해지지 않는다. 출고 직전 취소 가능 상태의 정확한 목록과 상태명은 OpenAPI·전이표에서 확정한다.

### 4.2 결제와 환불

```text
결제: READY → PROCESSING → SUCCEEDED / FAILED / UNKNOWN
UNKNOWN → 결제사 조회 → SUCCEEDED / FAILED / 운영자 확인
환불: REQUESTED → PROCESSING → SUCCEEDED / FAILED / UNKNOWN
UNKNOWN → 결제사 조회 → SUCCEEDED / FAILED / 운영자 확인
```

- 외부 호출 전에 처리 의도·주문번호·확정 금액·제공사 요청 식별자를 영속화한다.
- 외부 호출은 DB 트랜잭션을 오래 점유한 채 수행하지 않는다.
- 주문 소유권·결제 가능 상태·서버 확정 금액을 확인한다. 클라이언트의 인증 식별값만 믿고 승인하지 않는다.
- 결제 승인 성공을 재고 실패로 되돌리지 않는다. 결제 성공과 재고 확보 실패는 환불로 보상한다.
- 제공사 결제 ID 고유 제약·멱등키·누적 환불액 검사로 중복 승인·환불 반영을 막는다.
- 웹훅·승인 응답·대사가 같은 건을 처리해도 하나의 전이와 후속 이벤트로 수렴한다.
- 외부 요청 멱등성·웹훅 검증·타임아웃 이후 재승인 가능 조건은 토스페이먼츠 제품 계약을 확인해 별도 확정한다.

### 4.3 재고

```text
RESERVED → COMMITTED / RELEASED / EXPIRED
만료 뒤 승인 → 새 예약 세대로 재확보 → COMMITTED / 확보 실패
확정 재고의 환불 → 주문별 복원 기록
```

예약 시 가용 재고를 조건부 UPDATE로 감소시키고 예약 기록을 같은 트랜잭션에 저장한다. 여러 SKU는 ID 순으로 처리하고 하나라도 부족하면 전체 롤백한다. 예약 확정에서는 가용 재고를 다시 차감하지 않는다. 해제·만료·환불 복원은 각각 허용된 이전 상태에서 한 번만 수행한다.

초기 재고 확보 예시이며, 컬럼·SQL은 초안이다.

```sql
UPDATE inventory
SET available_quantity = available_quantity - :quantity
WHERE sku_id = :skuId
  AND available_quantity >= :quantity;
```

요청 수량은 양수이고 변경 행 수가 1이어야 성공이다. 중복 명령 방지 기록·예약 기록도 동일 트랜잭션에 포함한다. 예약·해제 명령에는 주문 ID뿐 아니라 **예약 ID·세대**를 넣어 이전 해제가 새 재확보를 취소하지 않게 한다. 해제가 먼저 도착하면 취소된 예약 의도를 기록해 뒤늦은 예약 생성을 거부한다.

예약 만료 판단은 재고 서비스 원장을 기준으로 한다. 30초 주문 중단 뒤 예약이 생기지 않도록 명령 유효기한과 상태 검사를 함께 적용한다. 만료·확정·재확보·환불 경합의 세부 전이표는 구현 전 작성한다.

## 5. Kafka 이벤트 계약 — 설계 제안

### 5.1 메시지 공통 필드

| 필드 | 의미 |
| --- | --- |
| `eventId` | 최초 생성 시 부여한 고유 ID. 재발행해도 유지 |
| `eventType`, `schemaVersion` | 메시지 종류·계약 버전 |
| `occurredAt`, `producer` | UTC 발생 시각·생산 서비스 |
| `aggregateId`, `aggregateVersion` | 대상 ID·원장 버전 |
| `correlationId`, `causationId`, `requestId` | 주문 흐름·원인 메시지·요청 추적 |
| `payload` | 명령 또는 사실에 필요한 최소 데이터 |

Kafka key는 주문 흐름에서 `orderId`를 기본으로 제안한다. 같은 파티션의 순서만 보장되며 토픽 간·다른 주문 간 순서를 가정하지 않는다. 같은 SKU의 서로 다른 주문 경합은 DB 조건부 UPDATE로 해결한다. 메일·주소·토큰·결제 시크릿을 이벤트에 불필요하게 복제하지 않는다.

### 5.2 명령과 결과 후보

| 생산 → 소비 | 메시지 후보 | 주요 데이터·처리 |
| --- | --- | --- |
| 주문 → 재고 | `ReserveInventory` | orderId, reservationId, generation, SKU·수량, commandExpiresAt |
| 재고 → 주문 | `InventoryReserved`, `InventoryRejected` | 예약 ID·세대, reservedAt, expiresAt 또는 거부 사유 |
| 주문 → 재고 | `ReleaseInventory` | 예약 ID·세대·사유. 선행 도착·중복 처리 허용 |
| 재고 → 주문 | `InventoryReleased`, `InventoryExpired` | 처리 결과, 재고 중복 복원 금지 |
| 결제 → 주문 | `PaymentSucceeded`, `PaymentFailed`, `PaymentUncertain` | paymentId, orderId, amount, currency, 결제 버전 |
| 주문 → 재고 | `CommitInventory` | 유효한 예약 확정. 만료된 예약이면 실패 결과 반환 |
| 재고 → 주문 | `InventoryCommitted`, `InventoryCommitRejected` | 출고 가능 여부 또는 재확보 필요성 |
| 주문 → 재고 | `ReacquireInventory` | 늦은 승인에 대한 새 예약 ID·세대 |
| 주문 → 결제 | `RefundPayment` | refundRequestId, paymentId, 전액 금액·사유 |
| 결제 → 주문 | `RefundSucceeded`, `RefundFailed`, `RefundUncertain` | 환불 ID·결과·버전 |
| 주문 → 재고 | `RestoreInventory` | 성공한 출고 전 환불에 대응하는 복원 키·확정 예약 ID |
| 재고 → 주문 | `InventoryRestored` | 복원 완료. 이미 해제한 예약에는 추가 복원 금지 |

실제 토픽명·파티션 수·보관 기간·재시도 토픽/DLQ는 미정이다. 지급·승인과 재고 확정을 묶는 분산 트랜잭션을 가정하지 않는다. 재고 확정 실패 시 주문 서비스가 재확보 또는 환불로 수렴시킨다.

### 5.3 Outbox·소비 처리

1. 업무 변경과 Outbox 삽입을 서비스 로컬 DB 트랜잭션으로 커밋한다.
2. 폴러가 미발행 행을 선점하고 Kafka 브로커 확인을 받은 뒤 발행 완료로 표시한다.
3. 발행 성공 후 완료 표시 전에 종료될 수 있으므로 중복 발행을 허용한다. `eventId`는 바꾸지 않는다.
4. 소비자는 업무 변경·소비 완료 기록·후속 Outbox를 같은 로컬 트랜잭션으로 저장하고, 커밋 후 offset을 반영한다.
5. 소비 기록은 `(consumer, eventId)`를 고유하게 관리하고, 업무 식별자에도 중복 방지 제약을 둔다.
6. 오래된 이벤트·역순 이벤트는 버전·허용 전이로 검사한다. 중복 기록이 있다고 미완료 업무를 성공으로 간주하지 않는다.

폴러 선점 만료·재시도 간격·독성 메시지 격리·기록 정리는 추가 설계한다. 단일 브로커에서 중단 후 재전달은 검증하지만 브로커 디스크 유실에 대한 복제 내구성은 보장하지 않는다.

## 6. 주요 처리 흐름 — 설계 제안

### 6.1 주문 준비

1. 주문 서비스가 상품·SKU의 현재 가격·판매 상태로 견적을 만들고 5분 기한을 저장한다.
2. 주문 요청에서 인증·소유권·배송지·약관·수량·견적 만료·가격을 재검증한다. 가격 조회 이후 변경은 예약 명령의 expectedUnitPrice와 카탈로그 조건부 UPDATE로 재검증한다. 확보 성공 후에는 주문 스냅샷 단가를 유지한다.
3. `PREPARING` 주문·명령 Outbox·멱등 결과를 커밋하고 `202`를 반환한다.
4. 재고 서비스가 모든 SKU 확보·예약·결과 Outbox를 한 트랜잭션으로 저장한다.
5. 주문 서비스가 성공 결과의 `reservedAt`·`expiresAt`을 반영하고 결제를 허용한다. 이미 중단했다면 해제 명령을 발행한다.
6. 30초 준비 기한 초과·예약 거부 시 결제를 차단하고 정리 작업을 추적한다.

### 6.2 승인과 복구

1. 결제 서비스가 주문 서비스에서 권위 있는 주문 금액·소유권·예약 기한·승인 가능 상태를 확인하고 결제 시도를 기록한다.
2. 외부 승인을 즉시 요청한다. 결과가 불명확하면 `UNKNOWN`으로 보존한다.
3. 결과·Outbox를 커밋하고 응답한다. 주문 서비스는 성공 이벤트 이후 재고 확정 또는 재확보를 요청한다.
4. 결제 서비스의 대사 작업은 서버 재시작 후 미완료 시도를 조회한다. 웹훅과 대사·HTTP 결과는 동일 원장에 수렴한다.
5. 예약 만료 후 미확정이면 재고를 해제한다. 늦은 승인은 새 재고 확보를 시도하고 실패 시 전액 환불한다.
6. 재시도 한도를 넘기면 운영자 확인 대상으로 남긴다. 재처리도 기존 멱등 식별자를 유지한다.

### 6.3 출고 전 취소

1. 주문 서비스가 출고와 경합하는 취소 의도를 원자적으로 확정하고 출고를 차단한다.
2. 결제 서비스에 환불을 요청하고 성공·실패·미확정을 별도 추적한다.
3. 환불 성공 후에만 확정 재고 복원을 요청한다. 미결제 예약 해제와 결제 후 재고 복원을 구분한다.
4. 재고 복원 결과까지 추적한다. 환불 성공 직후 종료돼도 Outbox 재전달로 후속 처리를 마친다.

## 7. 검증 계획 — 확정 목표와 설계 제안

장애 주입과 최종 상태 확인을 반복 실행 가능한 스크립트로 자동화한다. HTTP 성공 여부만으로 판정하지 않고 서비스별 원장·이벤트 처리 결과·외부 결제 결과를 대조한다.

| 단계 | 필수 시나리오 | 판정 기준 |
| --- | --- | --- |
| 결제 | 승인 성공 후 응답 유실·프로세스 종료·재시작 | 승인 결과 복구, 중복 승인·출고 없음 |
| 결제 | 중복 승인 요청·중복 웹훅·대사 경합 | 하나의 결제 결과와 재고 반영으로 수렴 |
| 결제 | 전액 환불 응답 유실·종료·중복 요청 | 누적 환불액이 승인액 이하, 재고 복원 한 번 |
| 결제 | 예약 만료 후 늦은 승인 | 재고 재확보 성공 시 유지, 실패 시 환불 |
| 결제 | 취소·출고 경합 | 한 처리만 선행 확정, 취소 접수 후 출고 차단 |
| 복구 | 결제사 장애 해소 | 자동 처리 대상은 1분 이내 복구 목표. 운영자 전환 건 별도 집계 |
| 메시징 | Kafka 중단·복구 | Outbox 보존 후 전달·처리 재개 |
| 메시징 | 발행 성공 직후 종료·소비 DB 커밋 직후 종료 | 재전달에도 업무 중복 반영 없음 |
| 메시징 | 예약·해제 역순, 30초 이후 성공 도착 | 유령 예약 없음, 중단 주문 결제 차단 |
| 재고 | 마지막 재고 1개에 동시 주문 100건, 두 앱 인스턴스로 분산 | 정확히 한 주문만 확보, 나머지 재고 부족, 음수 없음 |
| 재고 | 다중 SKU 중 하나 부족·교착·재시도 | 전체 롤백, 중복 예약·부분 확보 잔류 없음 |
| 조회 | 합성 상품 10만 개 | 필터·검색 정합성 확인, 실행 계획·P95·처리량·자원 사용 기록 |
| 보안 | 다른 회원 주문·장바구니 요청, 토큰 재사용·동시 갱신 | 소유권 차단, 세션 폐기, 정상 동시 갱신 처리 |
| 저장 | 병합 재시도·결제 중 장바구니 변경 | 중복 합산·의도하지 않은 삭제 없음 |

운영자 전용 API와 Swagger UI로 상품·재고·주문·환불·재처리를 관리한다. 운영 변경에는 행위자·대상·시각·요청 ID를 남긴다. 로그에 비밀번호·토큰·전체 주소·결제 시크릿을 남기지 않는다. 최소 메트릭은 미확정 건수·복구 지연·Outbox 미발행·소비 실패·재고 불일치를 포함하는 안으로 한다.

- east-west gateway·멀티클러스터: 결제·재고 검증 이후 네트워크 장애 실험. 단일 클러스터 Istio mTLS는 현재 구성에 포함하며 [적용 기반](istio-mtls.md)을 참고

- 부분 취소·반품·교환 셀프서비스, 회원 주소록, 택배사 조회

- 실제 판매 전: 상품·이미지 권한, PG 운영 계약, 개인정보 보관·삭제·탈퇴 정책, 반품·교환·배송 정책, 백업 복구·운영 가용성 검수

## 9. 구현 전 남은 결정과 진행 순서

### 미정 항목

- Kubernetes 버전. 프로젝트 골격의 Java·Spring Boot·MySQL·Kafka·Gradle 초기 버전은 [로컬 개발 환경](local-development.md)에 기록하며, 운영 이미지·업그레이드 정책은 별도 확정
- 두 서버의 제어 영역·워크로드·DB·브로커 배치, 영속 스토리지·백업, 복구 절차·자원 제한
- 도메인·TLS·외부 진입점·프론트 origin·쿠키 SameSite·CSRF·서비스 간 인증
- 폐기 세션의 액세스 JWT 즉시 거부, 서명키 관리·교체, 동시 리프레시 처리 정책
- 비밀번호 정책, 이메일 정규화·중복 기준, 인증 링크 만료·재발송·요청 제한, 미인증 가입 정리
- 실제 이메일 제공사·발송 제한, 토스페이먼츠 테스트 키·제품·콜백·웹훅 검증 계약
- Outbox 폴링·대사 주기·최대 재시도·백오프·DLQ·보관 기간. 1분 복구 목표와 일치하도록 설계
- API 요청·응답·오류·멱등키 수명·일괄 요청 상한, 이벤트 토픽·스키마·버전 호환
- 견적 시점과 주문 확정 시점 사이의 가격 버전 계약, SKU 판매 중지·가격 변경 경합
- 장바구니 변경 판별 방식. 삭제 조건은 SKU·수량 일치로 확정했으나 변경 후 같은 수량으로 돌아오는 경우는 버전 비교 등 추가 검토
- 10만 상품의 분포·검색어·조회 부하, P95·오류율 목표, 테스트 데이터 및 로그 디스크 예산

### 진행 순서

1. 서비스 데이터 소유권·상태 전이·명령/결과 계약을 검토하고 OpenAPI·이벤트 스키마를 작성한다. 목표 서비스 구성은 [아키텍처 문서](backend-architecture.md)를 기준으로 한다.
2. Java 등 버전과 서버 배치를 결정하고 Gradle 멀티모듈·개발용 MySQL/Kafka·마이그레이션을 구성한다.
3. 회원 인증, 상품·SKU, 저장 기능, 견적·비동기 주문·재고 예약의 기본 구매 경로를 연결한다.
4. 결제 테스트·모의 어댑터, 승인·전액 환불, Outbox·멱등 소비·대사·운영자 재처리를 구현한다.
5. 결제 장애 자동 실험을 먼저 통과시키고, 재고 100건 경합·조회 10만 상품 실험으로 확장한다.
6. 변경 전후 측정·실패 사례·복구 결과를 기록하고 실제 판매 전환 항목을 별도 검수한다.
