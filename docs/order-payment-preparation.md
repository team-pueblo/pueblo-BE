# 주문의 결제 시도 접수

주문 서비스가 결제 서비스에 제공할 내부 계약이다. 재고 확보가 끝난 주문의 금액·소유권·기한을 검증하고 결제 시도를 영속화한다. **PG 승인·결제 결과 이벤트·환불·재고 확정은 아직 구현하지 않았다.** 이 API의 200 응답은 결제 성공을 의미하지 않는다.

## 활성화와 인증

기존 주문·재고 설정에 추가한다. 기본값은 비활성이고 실제 `.env`는 변경하지 않았다.

```dotenv
ORDER_PAYMENT_PREPARATION_ENABLED=true
ORDER_PAYMENT_SERVICE_TOKEN=<32~256자의 별도 무작위 ASCII 비밀>
```

`ORDER_FLOW_ENABLED=true`도 필요하다. 비밀은 JWT 키·재고 HMAC 키와 분리하고 서버에만 주입한다. 활성화 상태에서 비밀이 없거나 형식이 잘못되면 앱 시작을 거부한다. Compose는 주문 서비스에 환경변수를 전달한다. 향후 결제 서비스 호출부에도 같은 비밀을 주입해야 한다.

내부 호출은 `X-Payment-Service-Token`을 검증한다. POST는 추가로 회원의 `Authorization: Bearer <accessToken>`을 전달하며 주문 서비스가 회원 API에서 폐기 여부를 포함해 확인한다. GET은 브라우저 토큰 만료 후 복구 작업을 위해 서비스 인증만 사용한다. 회원 JWT만으로 내부 API를 호출할 수 없다. Origin이 있는 요청은 거부한다.

배포 시 기존 Istio STRICT mTLS와 네트워크 접근 제한을 함께 적용한다. 공유 비밀 자체는 워크로드 신원 검증을 대신하지 않는다. 이번 작업에서 실제 클러스터 배포·mTLS 트래픽 검증은 수행하지 않았다. 내부 API는 브라우저 Swagger에서 숨겼다.

## 계약

| 메서드·경로 | 인증 | 응답 |
| --- | --- | --- |
| `POST /internal/v1/orders/{id}/payment-attempts` | 서비스 비밀 + 회원 JWT | 200, 최초 접수 또는 동일 시도의 현재 상태 |
| `GET /internal/v1/orders/{id}/payment-attempts` | 서비스 비밀 | 200, 저장된 시도와 현재 주문 상태. 미접수는 404 |

POST 본문:

```json
{
  "paymentId": "5b15004e-557f-46b5-9ecf-ad97130cf636",
  "amount": 39000,
  "currency": "KRW"
}
```

실제 금액은 주문 원장과 일치해야 한다. 응답은 공통 `data`·`requestId` 형식이며 data에 `orderId`, `paymentId`, `amount`, `currency`, `reservationId`, `createdAt`, `expiresAt`, `orderStatus`, `nextAction`을 포함한다. 주소·회원 개인정보는 제공하지 않는다.

- `CONTINUE_SAME_ATTEMPT`: 현재 주문이 결제 처리 중이고 예약 기한 안이다. 동일 시도에 한해서 후속 처리가 가능하다.
- `RECONCILE_ONLY`: 신규 승인 요청의 근거로 사용하지 않는다. 이미 요청한 결제의 제공사 결과 조회·대사가 필요하다.

응답은 조회 시점의 스냅샷이다. 응답 뒤 예약 만료가 발생할 수 있으므로 결제·재고의 분산 트랜잭션을 보장하지 않는다. 미래 결제 서비스는 외부 요청 전에 자신의 DB에 처리 의도와 paymentId를 저장하고, 제공사 멱등키를 유지해야 한다. 같은 응답을 받았다는 이유로 새 결제를 요청하지 않는다. 응답 유실·타임아웃 시 동일 시도를 조회하며 PG 성공/실패 여부를 별도로 확인한다.

## 원자성·상태·멱등성

주문 행을 `FOR UPDATE`로 잠근 뒤 소유권, 서버 금액, KRW, 예약 기한, `PENDING_PAYMENT` 상태를 확인한다. 결제 시도 저장과 `PAYMENT_PROCESSING` 전환은 한 로컬 트랜잭션이다. 외부 회원 API 호출은 이 트랜잭션 전에 수행한다.

현재는 주문당 결제 시도 1개다. paymentId도 전체 주문에서 고유하다. 같은 ID·금액·통화의 재접수는 저장된 ID와 기한을 유지하면서 현재 상태를 반환한다. 다른 ID는 409이며, 명확한 실패 이후 새 시도를 만드는 흐름은 후속 구현이다.

취소와 결제 접수는 같은 주문 행 잠금을 사용한다. 취소가 먼저 확정되면 접수가 거부되고, 접수가 먼저 확정되면 일반 미결제 취소가 거부된다. 결제 중 취소·환불은 아직 지원하지 않는다.

결제 처리 중 예약이 만료되면 주문은 `RECONCILIATION_REQUIRED`, 사유는 `PAYMENT_STATUS_UNKNOWN`이다. 해제 명령을 Outbox에 한 번 기록하고 재고 해제를 진행한다. 카탈로그가 먼저 만료 결과를 보내도 결제 실패로 바꾸지 않는다. 늦은 승인에 대한 재확보·자동 환불과 실제 PG 대사 작업은 후속 범위이므로 현재는 확인 필요 상태를 보존한다.

| 오류 | HTTP | 조건 |
| --- | --- | --- |
| `INVALID_CREDENTIALS` | 401 | 서비스 비밀 또는 회원 인증 실패 |
| `NOT_FOUND` | 404 | 없는 주문, 다른 회원 주문, 미접수 시도 조회 |
| `PAYMENT_AMOUNT_MISMATCH` | 409 | 원장과 다른 금액·통화 |
| `PAYMENT_ALREADY_STARTED` | 409 | 다른 결제 ID, 다른 주문에 사용된 ID, 처리 중 일반 취소 |
| `PAYMENT_NOT_READY` | 409 | 재고 확보 전 또는 접수 불가능 상태 |
| `PAYMENT_WINDOW_EXPIRED` | 409 | 최초 접수 전에 예약 기한 만료 |

## 마이그레이션·검증

V3는 V2의 MySQL 자동 이름 `customer_order_chk_2` 상태 제약을 명명된 제약으로 교체하고 `PAYMENT_PROCESSING` 및 `order_payment_attempt`를 추가한다. 기존 데이터를 삭제하지 않는다. 이전 버전 앱은 새 상태를 이해하지 못하므로 처리 중 주문이 있는 상태에서 이전 앱으로 단순 롤백하면 안 된다. 기능 플래그를 꺼도 시도 기록은 남고 주문 만료 처리는 새 상태를 계속 다룬다. 접수 기록의 보존·삭제 정책은 실제 판매 전에 확정한다.

검증 명령:

```sh
./gradlew :api-web:test :order-service:build :order-service:integrationTest
```

실제 MySQL 8.4.7·Kafka 4.1.2와 별도 주문/카탈로그 앱·DB 계정으로 검증한다. 추가 시나리오는 내부 인증·소유권·브라우저 차단, 금액·필수 입력·상태·기한 검증, 동일 시도 재접수와 고유 제약, 취소 경합, 동시 접수, 주문 측 만료·카탈로그 측 만료, 재시작 후 복구다. 회원 API는 계약 스텁이므로 실제 JWT 검증은 기존 회원 테스트의 범위다. 실제 SMTP·PG·사용자 로컬 DB는 사용하지 않는다.
